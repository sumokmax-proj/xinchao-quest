# 작업 흐름 안내 (오너용)

## 용어를 업무에 빗대면

| Git 용어 | 업무로 치면 |
| --- | --- |
| `main` 브랜치 | 운영(PROD). 항상 플레이 가능한 상태 |
| 브랜치 | 별도 작업 공간. 운영에 영향 없음 |
| 커밋 | 작업 중간 저장 기록 |
| PR (Pull Request) | "이 변경을 운영에 반영해도 될까요?" 승인 요청서 |
| 리뷰 | QC 검수 |
| Merge | 승인 후 운영 반영 → 자동 배포 |
| Conflict | 같은 파일의 같은 줄을 두 곳에서 다르게 고친 상황 |

## 웹/앱 Claude Code로 작업할 때

1. 요청한다. 예: "시장 단어 40개 words.json에 추가해줘"
2. Claude가 새 브랜치에서 작업하고 PR을 올린다
3. GitHub에서 PR을 연다
   - 설명란: 무엇을 바꿨는지, 폰으로 확인할 체크리스트
   - Files changed 탭: 초록 = 추가, 빨강 = 삭제
4. 이상 신호가 없는지 본다 (아래)
5. 필요하면 리뷰를 시킨다 (아래)
6. 괜찮으면 Merge → 몇 분 뒤 GitHub Pages에 자동 배포 → 폰으로 체크리스트대로 플레이
7. 문제가 있으면 PR 댓글이나 Claude Code 대화로 수정 요청. 별로면 PR을 닫으면 끝 (`main`은 그대로)

## 코드 몰라도 잡을 수 있는 이상 신호

- 요청과 상관없는 파일이 바뀌었다
- 빨간 줄(삭제)이 이상하게 많다
- `src/config.ts` 수치가 말없이 바뀌었다
- `package.json`에 새 라이브러리가 추가됐다

하나라도 보이면 "이건 왜 바꿨어?"라고 묻는다.

## 리뷰 시키는 법

코드를 짠 세션 말고 **새 세션**에서:

> PR #번호를 리뷰해줘. 버그 가능성, 요청 범위를 벗어난 변경, CLAUDE.md 규칙 위반, 손맛 기준값 변경 위주로. 자바스크립트 기초만 아는 사람이 이해할 수 있게 설명해줘.

이해 안 되는 부분은 "이 함수가 하는 일을 예시로 설명해줘"처럼 꼬리 질문.

## 역할 분담

| 검수 | 담당 |
| --- | --- |
| 동작 (폰으로 플레이) | 오너 |
| 코드 | 리뷰 전용 Claude 세션 |
| 베트남어 데이터 (성조, 북부 표현, 뜻) | Claude 1차 검수, 자신 없는 것만 오너 확인. 공개 전 베트남 사람 전체 검수 |

## 나중에 로컬 CLI를 병행할 때

- 로컬에서 시작 전 항상 `git pull`
- 손맛이 중요한 작업(조작감, 밸런스, 연출, 에셋)은 로컬, 데이터·문서·배포 설정은 웹
- 같은 파일을 양쪽에서 동시에 고치지 않기
- 충돌이 나면 Claude Code에 "충돌 해결해줘"
